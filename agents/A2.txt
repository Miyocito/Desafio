# A2 — Investigador de Patrones: Detección Básica

## Objetivo

Implementar únicamente la primera versión funcional del Agente 2 (A2) del sistema de detección de fraude.

A2 debe recibir múltiples resultados estructurados provenientes de A1, analizar las características comunes entre los casos y detectar posibles patrones de comportamiento fraudulento.

El agente debe utilizar procesamiento determinístico mediante Python para calcular frecuencias y agrupaciones, y un LLM para interpretar los indicadores encontrados y formular una **hipótesis de nuevo patrón de fraude**.

La salida debe ser un objeto estructurado y validado mediante Pydantic.

Esta implementación debe ser simple y estar preparada para ser extendida posteriormente con procesamiento batch, datasets históricos, logging, Streamlit, LangGraph y los agentes A3-A5.

---

# Alcance

Implementar solamente:

1. Modelo Pydantic para representar el resultado de A2.
2. Modelo Pydantic para representar los casos recibidos desde A1.
3. Integración con Google Gemini.
4. Análisis determinístico de los casos mediante Python.
5. Agrupación básica por:

   * modus operandi;
   * canal de fraude;
   * categoría de comercio;
   * comercio;
   * rango de monto.
6. Detección de frecuencias y concentraciones.
7. Prompt de interpretación en español.
8. Método `process_cases()`.
9. Generación de una hipótesis de patrón mediante el LLM.
10. Validación de la respuesta mediante Pydantic.
11. Un caso de prueba manual.

# 3. Modelo de hipótesis

Crear un modelo para representar una hipótesis detectada por A2.

Utilizar una estructura equivalente a:

```python
class HipotesisPatron(BaseModel):
    pattern_id: str
    hypothesis: str

    indicators: dict[str, str | list[str] | int | float | None]

    confidence: float = Field(
        ge=0.0,
        le=1.0
    )
```

El campo `hypothesis` debe contener una descripción clara del posible patrón.

Ejemplo:

```text
Posible campaña de vishing asociada a cargos no reconocidos
en comercios de tecnología.
```

La hipótesis debe considerarse una **posibilidad**, no una confirmación de fraude.

# 6. Método process_cases()

Implementar:

```python
def process_cases(
    self,
    cases: list[CasoA1]
) -> ResultadoA2:
```

Este método debe:

1. Recibir múltiples casos provenientes de A1.
2. Validar que cada caso tenga una estructura compatible con `CasoA1`.
3. Analizar los casos mediante Python.
4. Calcular los indicadores estadísticos básicos.
5. Identificar concentraciones relevantes.
6. Enviar los indicadores calculados al LLM.
7. Solicitar al LLM la interpretación de los indicadores.
8. Generar una o más hipótesis de posibles patrones.
9. Validar la respuesta mediante Pydantic.
10. Generar un `analysis_id`.
11. Agregar el timestamp del análisis.
12. Retornar un objeto `ResultadoA2`.

# 7. Análisis determinístico

El análisis estadístico básico debe realizarse mediante Python.

A2 debe calcular como mínimo:

### Frecuencia por modus operandi

Ejemplo:

```text
cargo no reconocido + vishing → 47
cargo no reconocido → 21
phishing → 12
```

### Frecuencia por canal

Ejemplo:

```text
telefono → 52
web → 21
app → 15
```

### Frecuencia por categoría de comercio

Ejemplo:

```text
tecnologia → 47
retail → 31
servicios → 12
```

### Frecuencia por comercio

Ejemplo:

```text
TechStore → 32
ElectroMarket → 15
CompuWorld → 8
```

### Estadísticas de monto

Calcular cuando existan datos suficientes:

```text
promedio
mediana
mínimo
máximo
```

No utilizar el LLM para realizar estos cálculos.

# 8. Manejo de valores nulos

A2 debe manejar correctamente los campos que A1 haya identificado como `null`.

Por ejemplo:

```json
{
  "ciudad": null,
  "pais": null
}
```

No se debe inferir ni inventar información geográfica.

Los valores nulos deben excluirse de las agrupaciones correspondientes.

Por ejemplo, si:

```text
ciudad = null
```

el caso no debe aparecer como una ciudad llamada `"null"`.

---

# 9. Detección de concentraciones

A2 debe identificar concentraciones simples utilizando los indicadores calculados.

Por ejemplo:

```text
47 de 100 casos
```

corresponden a:

```text
modus_operandi = vishing
canal = telefono
categoria = tecnologia
```

Esto representa una combinación potencialmente relevante.

La primera versión debe utilizar reglas simples y transparentes.

No implementar todavía algoritmos de Machine Learning ni clustering.

---

# 10. Prompt

El prompt debe estar en español.

A2 debe comportarse como un **investigador de patrones de fraude bancario**.

Su función es analizar indicadores previamente calculados y formular hipótesis sobre posibles patrones.

El LLM debe recibir los indicadores calculados por Python.

Debe buscar relaciones entre:

* modus operandi;
* canal;
* comercio;
* categoría del comercio;
* montos;
* frecuencia;
* comportamiento temporal cuando exista información suficiente.

Reglas importantes:

* No inventar información.
* No inventar casos.
* No inventar estadísticas.
* No modificar los valores calculados por Python.
* No afirmar que un patrón es fraude confirmado.
* No consultar información externa.
* No realizar cálculos estadísticos por cuenta propia.
* Las hipótesis deben basarse exclusivamente en los indicadores recibidos.
* Si no existe evidencia suficiente para identificar un patrón relevante, devolver una lista de patrones vacía.
* La salida debe ser exclusivamente JSON estructurado.
* No incluir explicaciones fuera del JSON.

El prompt debe indicar explícitamente el esquema esperado.

# 14. Regla importante sobre A3

A2 **NO debe consultar el histórico transaccional**.

A2 únicamente analiza los casos recibidos desde A1.

La validación contra transacciones históricas corresponde exclusivamente a A3.

El flujo esperado es:

```text
A1
 ↓
Casos estructurados
 ↓
A2
 ↓
Hipótesis de patrón
 ↓
A3
 ↓
Validación contra histórico
```

A2 no debe determinar:

* recurrencia histórica real;
* costo financiero;
* volumen financiero total;
* impacto económico;
* tasa de detección;
* falsos positivos.

Estos indicadores serán responsabilidad de A3 y A5.
